Schema Writing Guide

How Telepact schemas are structured.

Telepact schemas are JSON arrays of definitions. They can describe API functions, shared data models, global errors, and request/response headers with docstring-driven documentation.

Type expressions

Expression Meaning Notes
"boolean", "integer", "number", "string"Base scalar typesAppend ? to allow null.
["T"]Array of TArrays themselves are never nullable.
{"string":"T"}Map string keys to TObject keys are always strings.
"any"Any non-null JSON value"any?" allows null.
"struct.Name" / "union.Name" / "fn.name"Reference a top-level definitionFunction references are restricted inside top-level fn args.

Top-level definition kinds

Struct

Product type with named fields. Optional fields use a ! suffix in schema keys.

Union

Tagged sum type. Each tag maps to a struct payload, including empty structs.

Function

Request argument struct + result union. Result requires Ok_; non-Ok_ tags represent non-okay outcomes.

Errors

Global/systemic errors automatically merged into all user-defined function result unions.

Headers

Request/response header schema where fields start with @ and are implicitly optional.

Docstrings

Use "///" on top-level defs and union tags. Markdown is supported in console rendering.

Runtime-appended definitions

Standard

Utility functions and common validation errors (for example fn.ping_, fn.api_, parse/validation errors).

Auth

If you define struct.Auth_, Telepact can include @auth_ and auth-related standard errors.

Mock

When serving via mock server, Telepact adds stubbing and verification functions for test workflows.

Function definition

{
  "fn.compute": {
    "x": "number",
    "y": "number"
  },
  "->": [
    { "Ok_": { "result": "number" } },
    { "ErrorCannotDivideByZero": {} }
  ]
}

Message exchange

-> [{}, {"fn.compute": {"x": 6, "y": 3}}]
<- [{}, {"Ok_": {"result": 2}}]
